# SmokeHere PRD 작성 스킬

SmokeHere는 "빠르게 흡연구역을 찾는다"는 단 하나의 핵심 문제에 집중하는 서비스입니다. PRD가 산만해지면 이 초점이 흐려지므로, 이 스킬은 항상 **필수 기능과 추후 기능을 명확히 분리**하고, 이미 확정된 아키텍처 결정(Route Handler 캐싱, LocalStorage, Google Maps 딥링크)을 무너뜨리지 않는 방향으로 문서를 작성합니다.

## 왜 이 순서로 하는가

사용자가 아이디어를 말로 풀어놓을 때는 배경 → 기능 → 제약이 뒤섞여 나옵니다. 이걸 그대로 받아적으면 "필수"와 "추후"가 섞인 산만한 문서가 됩니다. 그래서 먼저 이미 알고 있는 SmokeHere 컨텍스트를 불러와 기준선을 잡고, 이번 대화에서 나온 새 정보를 그 기준선 위에 병합한 뒤, 빠진 부분만 질문하는 순서를 따릅니다.

## 1단계: 기존 컨텍스트 불러오기

`references/smokehere-context.md`를 읽으세요. 이 파일은 SmokeHere의 미션, 확정된 아키텍처 결정, 필수/추후 기능 목록을 담고 있는 살아있는 기준 문서입니다. PRD를 쓸 때마다 이 내용을 처음부터 다시 묻지 마세요.

이번 대화에서 사용자가 이 파일에 없는 새로운 결정이나 기능을 이야기했다면, PRD 작성 후 `references/smokehere-context.md`도 함께 갱신하세요. 이 파일이 최신 상태를 유지해야 다음 PRD 작성 시에도 재사용할 수 있습니다.

## 2단계: 이번 요청의 범위 파악

사용자가 이번에 이야기한 내용이 다음 중 무엇에 해당하는지 판단하세요:

- **전체 서비스 PRD**: 처음 만드는 경우, 또는 서비스 전체를 다시 정리해달라는 요청
- **특정 기능 PRD**: 이미 있는 PRD에 새 기능(예: QR 코드 검색, 금연 캠페인 알림)을 추가하는 요청

특정 기능 요청인데 관련 기존 PRD 파일이 `docs/prd/`에 있다면, 새 파일을 만들지 말고 그 문서에 섹션을 추가하는 것이 맞는지 먼저 사용자에게 확인하세요.

## 3단계: 빠진 정보 질문하기

`assets/prd_template.md`의 섹션을 채우는 데 필요한 정보 중, 컨텍스트 파일과 이번 대화 어디에도 없는 것이 있다면 한 번에 하나씩 질문하세요. 특히 다음은 추측하지 말고 반드시 확인하세요:

- 성공지표(성공을 어떻게 측정할지)가 구체적인 숫자나 지표로 없는 경우
- 필수 기능과 추후 기능의 경계가 애매한 항목
- 비기능 요구사항 중 수치가 필요한 것(캐싱 주기, 응답 속도 목표 등)

이미 답이 나와있는 내용을 다시 묻지 마세요.

## 4단계: PRD 작성

`assets/prd_template.md`를 기반으로 다음 섹션을 채우세요:

1. **배경 및 문제 정의** — 왜 만드는지, 어떤 불편함에서 시작했는지
2. **목표 및 성공지표** — 이 서비스가 성공했다고 판단할 기준
3. **사용자 시나리오 / 유저 플로우** — 실제 사용자가 서비스를 쓰는 흐름을 스토리 형태로
4. **기능 요구사항** — 필수(MVP) 기능과 추후 기능을 표나 목록으로 명확히 구분
5. **비기능 요구사항** — 성능, 캐싱 정책, 데이터 정합성, 보안/개인정보(로그인 없음에서 오는 제약) 등
6. **범위 제외(Out of Scope)** — 이번 MVP에서 의도적으로 하지 않는 것과 그 이유

각 섹션은 확인되지 않은 내용을 지어내지 마세요. 모르는 건 "확인 필요"로 표시하고 사용자에게 물어보세요(3단계에서 이미 물었다면 답변을 반영).

## 5단계: 저장 및 검토 요청

- 파일명: `docs/prd/YYYY-MM-DD-<주제>.md` (주제는 영어 kebab-case, 예: `2026-08-08-smokehere-mvp.md`)
- 저장 후 사용자에게 검토를 요청하세요. 커밋은 사용자가 명시적으로 요청할 때만 하세요.
- `references/smokehere-context.md`에 반영할 새 정보가 있었다면 함께 갱신했음을 알리세요.

## 자체 검토 체크리스트

문서를 저장하기 전에 스스로 확인하세요:

- [ ] "TBD", "추후 논의" 같은 방치된 placeholder가 없는가
- [ ] 필수 기능과 추후 기능이 한 목록에 섞여 있지 않은가
- [ ] 성공지표가 측정 가능한 형태인가 (막연한 "많이 쓰인다" 대신 구체적 기준)
- [ ] 비기능 요구사항이 이 프로젝트의 실제 결정(캐싱 24시간, LocalStorage, 로그인 없음)과 모순되지 않는가
