# Git Commit 생성 스킬

커밋 메시지 하나만 잘 쓰는 게 목표가 아니라, 커밋에 들어갈 변경사항 자체가 원자적이고 검증된 상태인지까지 책임지는 스킬입니다. 린트를 건너뛰거나 서로 무관한 변경을 한 커밋에 욱여넣으면 나중에 `git log`나 `git blame`으로 히스토리를 추적할 때 의미가 사라지므로, 아래 순서를 그대로 따르세요.

## 프로세스

1. **`npm run lint` 실행** — 실패하면 커밋을 진행하지 말고 오류를 먼저 사용자에게 보여주거나 수정하세요. 린트를 통과하지 못한 코드가 히스토리에 남으면 이후 커밋들이 그 위에 계속 쌓이게 됩니다.
2. **스테이지된 파일 확인** (`git status`) — 이미 스테이지된 파일이 있다면 그 파일만 커밋 대상으로 삼으세요. 스테이지된 파일이 없다면 `git status`/`git diff`로 전체 변경사항을 파악한 뒤 사용자와 함께 무엇을 스테이지할지 결정하세요.
3. **diff 분석** — 스테이지(또는 스테이지 예정) 변경사항이 서로 다른 관심사를 담고 있는지 확인하세요. 판단 기준:
   - 서로 다른 관심사 (예: 버그 수정 + 새 기능)
   - 혼합된 커밋 타입 (feat + docs가 섞임)
   - 무관한 파일 패턴 (설정 파일 vs 컴포넌트 코드)
   - 지나치게 큰 변경사항
4. **필요시 분할 제안** — 위 기준에 걸리면 사용자에게 몇 개로 나눌지, 어떤 파일을 묶을지 먼저 제안하고 동의를 구한 뒤 진행하세요. 되돌리기 어려운 작업은 아니지만, 사용자가 의도한 것과 다른 파일이 한 커밋에 섞이면 히스토리가 지저분해집니다.
5. **컨벤셔널 포맷으로 커밋 생성**

## 커밋 메시지 포맷

`<타입>: <설명>`

**타입:**

- `feat`: 새로운 기능
- `fix`: 버그 수정
- `docs`: 문서화
- `style`: 포맷팅
- `refactor`: 코드 리팩토링
- `perf`: 성능 개선
- `test`: 테스트
- `chore`: 빌드/도구

**규칙:**

- 한글, 명령형 어조로 작성 ("추가" not "추가됨")
- 첫 줄은 72자 미만
- 원자적 커밋 (커밋 하나 = 목적 하나)
- **커밋 메시지에 Claude 서명을 절대 추가하지 않음**
